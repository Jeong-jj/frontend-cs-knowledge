# PR 열기

PR 하나가 `main` 에 커밋 하나로 남는다. **PR 본문이 이 저장소의 공개 학습 이력이다.**

## 0. 어느 시점인지 먼저 가른다

**PR 은 주제 단위다. 하루 단위가 아니다.** 당일 기록은 `sessions/` 가 맡는다.

```text
주제 첫날    커밋 → push → draft PR 을 연다        (아래 A)
이후 매일    커밋 → push                          (PR 은 그대로 둔다)
주제 완료    본문 여섯 절을 채우고 ready 로 바꾼다   (아래 B)
```

```bash
gh pr view --json isDraft,title 2>/dev/null || echo "PR 없음"
```

PR 이 없으면 **A**, 이미 draft 로 있으면 **B** 다. 인자가 `ready` 면 바로 B 로 간다.

며칠치 커밋이 로컬에만 있으면 유실된다. **첫날 draft 를 열어 매일 원격에 올린다.**

---

## A. 주제 첫날 — draft 로 연다

### A-1. 분기점을 본다

```bash
git branch --show-current
git --no-pager log --oneline main..HEAD
```

**여기 뜨는 커밋이 전부 이 주제의 것이어야 한다.** 남의 것이 섞여 있으면
브랜치를 `main` 에서 다시 갈라 필요한 커밋만 체리픽한다.

### A-2. 담긴 것을 본다

```bash
git --no-pager diff --stat main..HEAD
```

`sessions/` 아래 파일이 있으면 **멈춘다.** 개인 학습 기록은 공개하지 않는다.

### A-3. 제목을 짓고 검사한다

**PR 제목이 그대로 `main` 의 커밋 제목이 된다.** 스쿼시 머지라서다.

```bash
scripts/check-title.sh "<제목>"
```

**제목은 정리한 것을 가리킨다. 한 일을 가리키지 않는다.**

```text
나쁨  note(browser): 1주차 학습 내용 반영
좋음  note(browser): 렌더링 파이프라인 4단계 정리
```

주제가 끝나기 전이라 제목이 확정되지 않을 수 있다. **완결 시점의 제목으로 미리 짓는다.**
B 단계에서 바뀌면 그때 고친다.

### A-4. 본문은 뼈대만 둔다

`.github/pull_request_template.md` 의 절을 그대로 두고, `요약` 의 **답하는 질문**
한 줄만 채운다. 나머지는 비워 둔다. **draft 이므로 미완성이 정상이다.**

이 단계에서 `- 없음` 을 쓰지 않는다. `- 없음` 은 판단한 결과로 없다는 뜻이지
아직 안 썼다는 뜻이 아니다.

### A-5. 확인받고 연다

원격에 나가는 일이므로 **사용자에게 묻고 한다.**

```bash
git push -u origin <브랜치>
gh pr create --draft --label "area:<scope>" --title "<제목>" --body-file <파일>
```

**축은 `area:` 하나다.** 아홉 개가 커밋 제목의 scope 와 일대일로 대응한다.
저장소에 이미 만들어져 있다.

```text
area:browser  area:http  area:network  area:runtime
area:security  area:perf  area:os  area:interview  area:meta
```

GitHub 기본 라벨(`bug` `documentation` `enhancement` `question` 등)은 지웠다.
`documentation` 은 저장소 전체가 문서라 아무것도 구분하지 못하고, `bug` 와
`enhancement` 는 제목의 `fix` 와 `note` 가 이미 하는 일이다. 두 곳에서 관리하면
어긋난다.

**축이 둘 이상이면 매번 조합을 고민하게 되고, 그 마찰로 라벨이 안 붙는다.**
상태 축(`blocked`, `needs-decision` 등)이 필요해지면 그때 만든다.
쓸 일이 생기기 전에 만든 라벨은 쓰이지 않는다.

## B. 주제 완료 — 본문을 채우고 ready 로 바꾼다

### B-1. 단위를 본다

**PR 하나는 완결된 주제 하나다.** 제목에 `그리고` 가 들어가면 쪼갠다.

되돌릴 때 커밋 하나만 revert 하면 되고, 이력을 주제 단위로 읽을 수 있다.

### B-2. 담긴 것을 다시 본다

```bash
git --no-pager log --oneline main..HEAD
git --no-pager diff --stat main..HEAD
```

`sessions/` 가 뜨면 멈춘다. 며칠에 걸친 브랜치라 A 때 없던 것이 섞였을 수 있다.

### B-3. 제목을 확정하고 검사한다

주제가 끝났으므로 이제 정확한 제목을 지을 수 있다.

```bash
scripts/check-title.sh "<제목>"
gh pr edit --title "<제목>"
```

### B-4. 본문을 템플릿대로 채운다

**절을 하나도 지우지 않는다.** 쓸 내용이 없으면 `- 없음` 한 줄을 남긴다.

```text
요약          답하는 질문 한 줄과, 도달한 답의 요지
근거와 확인    1차 출처 / 재현 결과 / 확인 못 한 것
설명 점검      어느 길이까지 소리 내어 해봤는지. 꼬리 질문 대응 단수
구성 판단      기초와 심화를 가른 기준. 뺀 것과 그 이유. 쪼갤 조건
참고          앞선 문서와의 연결. 앞으로 쓰일 곳. 추가한 glossary 용어
남은 것        검증 TODO. 다루지 않은 것과 이유. 다음 문서 단위
체크리스트      일곱 항목
```

**모든 PR 이 같은 구조를 갖게 하려는 규칙이다.** 절이 실행마다 달라지면
두 PR 을 나란히 놓고 볼 수가 없다.

`- 없음` 은 판단한 결과로 없다는 뜻이다. **아직 안 썼다는 뜻으로 쓰지 않는다.**
덜 썼으면 draft 로 두고 비워 둔다.

본문은 평서형과 명사형으로 쓴다. 구어체 존댓말을 쓰지 않는다.
**학습 과정이나 감상이 아니라 문서에 반영된 결과를 쓴다.**

며칠치 커밋이 쌓여 있으므로 `git log main..HEAD` 를 훑어 본문의 재료로 쓴다.

#### 근거와 확인 을 빈칸으로 두지 않는다

**이 저장소의 최대 리스크는 틀린 내용을 공개하는 것이다.** 이 절이 그것을 막는다.

단정해서 쓴 내용마다 1차 출처를 댈 수 있어야 한다. 스펙이나 공식 문서로 확인하지
않고 쓴 것은 본문에서 내려 `검증 TODO` 로 옮긴다.

개발자도구나 코드로 재현하지 못했으면 **못 했다고 적는다.**
확인 못 한 것을 적는 것이 이 절의 절반이다.

### B-5. 체크리스트를 실제로 보고 채운다

체크리스트는 두 갈래다. `학습 문서 PR` 항목과 `모든 PR` 항목이다.

```text
학습 문서 PR
- [ ] 문서 하나가 질문 하나에 답한다
- [ ] 30초·2분·심화 답변을 소리 내어 해봤다
- [ ] 꼬리 질문에 2단계 이상 대응된다
- [ ] 단정한 내용은 모두 근거가 있다. 추측은 검증 TODO 로 내렸다
- [ ] 본문에 학습 과정이나 감상이 남아 있지 않다
- [ ] README.md 에서 이 문서로 링크된다

모든 PR
- [ ] scripts/check-title.sh 로 제목을 검사했다
```

**사람만 판단할 수 있는 것만 있다. 안 보고 누르면 아무도 안 본 것이 된다.**

기초와 심화가 나뉘어 있는지, 세 길이 답변이 있는지는 grep 으로 센다.
여기서 묻는 것은 **실제로 소리 내어 해봤는가** 다.

스킬이나 설정을 고치는 PR 은 학습 문서 항목이 해당되지 않는다.
**항목을 지우지 않고 `- [-]` 로 둔다.** 절을 지우지 않는 것과 같은 이유다.

빈 칸으로 남길 때는 왜 그 상태로 머지하는지 본문에 적는다.

### B-6. 확인받고 ready 로 바꾼다

```bash
gh pr edit --body-file <파일>
gh pr ready
```

## 머지 뒤

- 브랜치를 지운다
- `sessions/progress.md` 에서 끝난 주제의 상태를 `학습완료` 로 갱신한다
